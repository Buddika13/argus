01 · briefThe brief, restated

Every ISP and organisation runs a caching DNS resolver. A caching resolver can be poisoned — an attacker races a forged reply to the user before the real one arrives, and the cache then serves a wrong address to everyone behind it. ARGUS watches those resolvers, nationwide, from one central machine, and reports whether any of them is being hijacked.

The supervisor's instruction sets five fixed points, and the interface is designed around them rather than around a generic dashboard:

fixed point

Centralised

One machine runs the whole watch, not an agent per network. The header always shows which vantage and timezone the numbers come from.

fixed point

Every five minutes

The sweep cadence is a property of the system, shown in the header and provable from the stored timestamps.

fixed point

Sri Lankan resolvers

The public caching resolvers of SL networks are the subjects; the machine holds the list and checks each for hijacking.

fixed point

Authoritative is truth

Ground truth is the answer walked from the root to the zone's own servers — not a trusted third party, which could itself be wrong.

fixed point

Answers are sets

A domain may hold three or four addresses for load balancing, so answers are compared as sets, and a partial overlap is not a hijack.

02 · mechanismThe detection mechanism, made visible

This is the one screen the whole product exists for, so the interface makes the comparison literal: the two resolution paths sit side by side, and the verdict is the relationship between their address sets.

Untrusted path — the monitored cache

dig @<resolver-ip> <domain> A

What the ISP's caching resolver claims. An attacker who wins the race has planted a wrong answer here. Never trusted.

vs

Trusted path — walked from the root

dig +trace <domain> A

Root → TLD → authoritative, resolved independently with no cache in the way. This is ground truth.

MATCHAddress sets equal
PARTIALSubset — load balancing
MISMATCHUnpublished IP → possible hijack
ERRORTimed out / unreachable

The comparison is set arithmetic, so a resolver returning 4 of a domain's 5 load-balanced addresses reads as PARTIAL, not a hijack. A MISMATCH — an address the zone never published — is the fingerprint that can escalate, and only after a six-stage check is it ever called possible poisoning. It is never called proven.

03 · principlesDesign principles

Five rules govern every screen. They come straight from what the system is for, and they are the reason the interface looks the way it does.

01

Real data or an empty state

Never a fabricated number. Where the database has nothing, the screen says so plainly instead of filling the space with a plausible-looking figure.

02

Evidence, not assertion

Every verdict can be opened to the two dig commands and the two answers behind it, so a finding is reproducible by hand — what a research write-up needs.

03

State reads at a glance

Severity and result are carried in shape and colour — a coloured disc, a pill — not only in a word, so the one row that needs attention is visible without reading.

04

Careful language

"Possible", never "confirmed". The interface never overstates what a passive observer can know, and always offers the legitimate explanations a difference was tested against.

05

Scanned, not read

It is an operations tool: the summary comes before the detail, tables stay compact, and what is interactive looks interactive.

Palette

A deep navy carries the identity through the sidebar and header; a single blue accent marks what is active or clickable. Semantic colour — green, amber, red — is reserved for verdicts and never used decoratively, so a red mark on any screen always means the same thing.

Signature components

Three components do most of the work and recur across screens, so the same state always looks the same.

✓MATCH !PARTIAL ×MISMATCH −ERROR

The result pill — a coloured disc with a glyph and the word — is the atom of the Results and Alerts tables. Severity uses the same disc in High / Medium / Low. The two-path evidence card (red untrusted, green trusted) is the third recurring object, shown in full on the Monitoring screen below.

07 · statusHonest status

The interface and the engine are built and working against real data — 1,785 measurements, 30 investigated anomalies — but on the five global public resolvers used as the control baseline (Google, Cloudflare, Quad9, OpenDNS, Verisign).

The one open step. The Sri Lankan ISP resolvers — SLT, Mobitel, Dialog, Hutch — are configured but hold placeholder addresses and are disabled, so no SL resolver is being checked yet. Real resolver IPs, read from a Sri Lankan connection, must be entered before the system does the nationwide job the brief describes. This is a data step, not a design one: the screens above already accommodate them.

Two enhancements would answer the supervisor's "query as many nameservers as possible" and "make it sophisticated" points: asking every authoritative nameserver for a zone and requiring agreement, and DNSSEC-validating the trusted walk itself so an on-path attacker cannot forge ground truth.
